\section{Pseudo-injective estimation: an attempt for an injective mixing 
\texorpdfstring{$g$}{g} with a regularized VAE}
\label{sec:pseudoinj}

\Cref{sec:flow} proposed a flow head to get an exactly invertible $g$.
It was abandoned before implementation: an exactly invertible map cannot reduce dimension
(\cref{sec:flow:motivation}), so a square injective flow head is structurally the wrong shape for M1, 
which needs roughly ten output latents, not a $150{,}528$-dimensional one.
\footnote{$224\times224\times3$} 
This section proposes what replaces it: not an exact diffeomorphism, but a pair of networks -- a 
frozen, pretrained backbone and a 
trainable head -- each carrying an explicit, measurable regularizer that keeps them \emph{close to} 
\textbf{injective}, while actually reducing dimension the way \nameref{sec:archB} does. 
We first restate the problem this is meant to solve, then the alternatives that were considered and set 
aside, then the two pieces of the proposed pipeline (\cref{sec:pseudoinj:invae,sec:pseudoinj:blae}), 
then a first, wrong version of the
training objective and why it had to be corrected (\cref{sec:pseudoinj:jacobian}), then the corrected
architecture (\cref{sec:pseudoinj:arch}), and finally an explicit list of gotchas
(\cref{sec:pseudoinj:gotchas}) that a reader implementing this should not discover the hard way.
The code that implements this section is \texttt{invae.py} and \texttt{extract\_features.py} (frozen
backbone), \texttt{head.py} (trainable head), \texttt{losses.py} (all loss terms) and
\texttt{geodesic.py} (the geodesic table); none of it has been run yet on real TI data
(\cref{sec:schedule}).

\subsection{The problem this section answers}
\label{sec:pseudoinj:problem}
\Cref{sec:arch} already states the gap in \nameref{sec:archA} and \nameref{sec:archB} plainly: a frozen ResNet-50 is
provably non-injective (any pooling convnet is), so nothing constrains $\mathrm{BB}\circ g^{-1}$ to be
injective, differentiable, or otherwise well-behaved, and the gap is \emph{unexamined} -- nothing in the
pipeline measures how bad it is. \Cref{sec:flow} closed that gap exactly, at the cost of being unable to
reduce dimension. What is wanted is a middle position: a backbone and a head that are not exactly
injective, but whose deviation from injective is bounded and estimated, not ignored, while still landing
at M1's small latent dimension (\emph{``pseudo-injective''}).

\subsection{Alternatives considered and set aside}
\label{sec:pseudoinj:discarded}
\begin{itemize}[leftmargin=1.5em]
\item \textbf{Rectangular (injective) flows} \cite{caterini2021}. These are the flow family that can, in
      principle, reduce dimension while staying exactly injective, by computing the Gram determinant
      $\det(J^\top J)^{1/2}$ instead of a square Jacobian determinant (\cref{sec:flow:injective}). Set
      aside: the published results barely reach CIFAR-10 scale, not ImageNet-scale full-resolution 
      images, and computing (or differentiating) the Gram determinant is itself an open research 
      problem, not an engineering cost.
\item \textbf{A $(z,w)$ padding variant.} Keep an exactly bijective, dimension-preserving flow as in
      \cref{sec:flow}, but declare only the first $\sim\!10$ coordinates of its output ``$z$'' (M1's
      latent) and treat the rest as a nuisance padding vector $w$, discarded after training. Set aside:
      this sits outside \cref{thm:ng} as written (the theorem is stated for $Z$ itself, not a marginal or
      a projection of a larger vector with no constraint tying $w$ to anything), and it does not obviously
      buy anything \nameref{sec:archB} does not already give more cheaply.
\end{itemize}

\subsection{IN-VAE: a pretrained, frozen, reconstruction-trained backbone}
\label{sec:pseudoinj:invae}
\textbf{What it is.} A large, pretrained image autoencoder of the kind used as the first stage of latent
diffusion pipelines: an encoder/decoder pair trained end-to-end on a reconstruction (plus, depending on
the variant, adversarial and/or perceptual) objective at ImageNet scale, whose \emph{encoder} we reuse
frozen as BB, exactly as \nameref{sec:archB} reuses a frozen ResNet-50. We call this class \textbf{IN-VAE}
in this note: pseudo-injective not because any Jacobian argument certifies it, but because reconstruction
training directly rewards the encoder-decoder pair for approximately undoing each other, which a
classification objective (plain ResNet-50, or the supervised-pretraining case of \cref{sec:pretrain}) has
no reason to do at all. Unlike \nameref{sec:archB}'s pooled $\sim\!3072$-dim vector, IN-VAE's output is a
\emph{spatial} latent, a tensor of shape $C\times h\times w$ (concretely $32\times16\times16$ for the
chosen candidate, \cref{sec:pseudoinj:arch}), not a flattened, globally pooled embedding -- this is
relevant to the head architecture below.

\textbf{Candidates surveyed.} SD-VAE kl-f8 (embedding width $4096$),
\footnote{the regularization type on the latent: KL-regularized, $\times$8 spatially downsampled}
the IN-VAE/REPA-E baseline used in
this note ($8192$), E2E-VAE ($8192$-class, but its representation-alignment loss is trained to match a
downstream generative model's preferred feature geometry, which is exactly the kind of pressure
\cref{sec:pretrain} already flags as likely to squeeze out style/location cues), FLUX/SD3 VAE
($16384$), DC-AE, and MAETok/STELLAR (semantically-shaped tokenizers, same style-squeezing risk as
E2E-VAE, for a different reason: their objective explicitly rewards semantic/content compression). Every
candidate carrying this alignment or semantic-shaping risk -- E2E-VAE, MAETok, STELLAR -- must be screened
with the linear-probe diagnostic of \cref{app:probe} (species accuracy plus within-species location
accuracy) before it is used, exactly as \cref{sec:pretrain} already requires for the ResNet-50 case; none
of them is used or discussed further in this note.

\textbf{Why IN-VAE (the REPA-E-style baseline) \cite{leng2025repae} is the default here.} It is 
trained on plain reconstruction (plus KL, MSE, LPIPS and GAN terms),
\footnote{The terms:
\begin{itemize}[topsep=0pt]
\item Learned Perceptual Image Patch Similarity (LPIPS). Instead of comparing pixels, it passes $x$ 
   and $\hat x$ through a fixed pretrained network (VGG or AlexNet) and compares their intermediate 
   features. This penalizes differences in texture and structure that MSE tolerates, so 
   reconstructions look less blurry.
\item GAN (adversarial). A discriminator, usually patch-based, learns to tell real images from 
   reconstructions. The decoder is rewarded for fooling it, which sharpens fine detail.
\end{itemize}
}
with no alignment or semantic-shaping loss pulling it toward
discarding style/location information; its embedding width ($8192$, i.e.\ $32\times16\times16$) is
comparable to the other non-flagged candidates; and it needs no bespoke training code, only a frozen
forward pass -- the same iteration-speed argument \cref{sec:archB} already makes for a frozen backbone.
Everything from here on assumes this choice; it should still pass \cref{app:probe}'s screen before being
trusted, the same as any candidate.

\textbf{How the frozen encoder is run} (\texttt{invae.py}, \texttt{extract\_features.py}). The 
released IN-VAE is REPA-E's own \texttt{AutoencoderKL} class (a port of the CompVis latent-diffusion 
VAE, loaded from a clone of their repository with a strict state-dict load), \emph{not} the Hugging 
Face original \linebreak
\texttt{diffusers.AutoencoderKL} that the trainable head uses  
(\cref{sec:pseudoinj:arch}). The facts that matter for the pipeline:
\begin{itemize}[leftmargin=1.5em]
\item the cached $\tilde x$ is the posterior \emph{mean} of the encoder (deterministic, no sampling, 
      no gradient);
\item input range is $[-1,1]$, with no ImageNet mean/std normalization;
\item it is trained at $256\times256$, giving a $(32,16,16)$ latent, so images must be $256\times256$
      (the tools do not resize);
\item it uses GroupNorm only: there is no BatchNorm and nothing to recalibrate to TI, so stage~1 of
      \nameref{sec:archB} does not exist here;
\item the brightness scalar of \cref{sec:use} is computed from the input image before any
      normalization, as in \nameref{sec:archB}.
\end{itemize}

\subsection{BLAE: an injective/bi-Lipschitz regularizer for the trainable head}
\label{sec:pseudoinj:blae}
\textbf{What it is.} Zhan et al.\ \cite{zhan2026blae} assume that high-dimensional data resides
on a $k$-low-dimensional manifold $\Mk \subset \R^m,\ k = \dim(\Mk)$ and that there's an autoencoder 
that learns this intrinsic representation through a pair of parametrized mappings 
$(\E_\theta,\D_\phi)$:
\begin{itemize}
\item The encoder $\E_\theta : \R^m \to \R^n (k < n \ll m)$ compresses data onto a low-dimensional 
      latent space;
\item The decoder $\D_\phi : \R^n \to \R^m$ reconstructs the original data from the latent 
representation.
\end{itemize}

They propose two separate losses to add to an otherwise ordinary autoencoder, meant to push it
toward being injective without requiring an exactly invertible architecture. In this note they are the
terms INJ and BILIP, implemented in \texttt{losses.py} after the released BLAE code, and they act on
different objects.
\begin{itemize}[leftmargin=1.5em]
\item The \emph{injective} loss (INJ) acts on the \emph{encoder side}. For pairs of inputs in a
      minibatch whose geodesic distance is above $5\%$ of the batch maximum (and whose latent distance
      is nonzero) it looks at the ratio $r=\lVert z_i-z_j\rVert/d_{\mathrm{geo}}(x_i,x_j)$ and penalizes
      $\mathrm{ReLU}(\log 0.3-\log r)+5\,\mathrm{ReLU}(r-1)$, averaged over pairs. That is, it keeps
      latent distances between $0.3$ and $1$ times the geodesic distances of the inputs: distinct
      inputs cannot collapse to one latent (lower bound), nor be stretched apart (upper bound). The
      geodesic distances are estimated once by an Isomap-style shortest-path computation
      (\cref{sec:pseudoinj:gotchas}). The paper's Theorem~1 gives a separation criterion; the loss
      implemented is the released \texttt{InjectiveLoss}.
\item The \emph{bi-Lipschitz} regularization term (BILIP) acts on the \emph{decoder side}
      and uses no geodesic table (as opposed to the INJ term). 
      With $J=\partial\,\mathrm{decode}/\partial z$ (a $P\times D$ matrix, $P$ the dimensionality of 
      input $\tilde x$) it has two variants, named
      after the \texttt{reg\_grad} values of the released BLAE code and selected by
      \texttt{loss.bilip\_variant}; the choice is the user's
      (\cref{sec:schedule:objects}). Both compute $J$ by forward-mode differentiation
      on a random fraction ($0.3$) of the batch.
      \begin{itemize}[leftmargin=1.3em]
      \item \texttt{bi-lipschitz\_dec} is \cite[Eq.~(12)]{zhan2026blae}. With
	        \[
	        \ell_{\mathrm{biLip}}=
	        \mathbb{E}\left[\left(\mathrm{ReLU}\left(\tfrac{1}{\kappa}-\sigma_{\min}\right)\right)^2
	        +\left(\mathrm{ReLU}\left(\sigma_{\max}-\kappa\right)\right)^2\right], 
	        \qquad \kappa\ge1,
	        \]
            so the singular values are kept in $[1/\kappa,\kappa]$: no latent direction is
            collapsed beyond $1/\kappa$, none is stretched beyond $\kappa$. 
            Both extremes come from one \texttt{torch.linalg.svdvals} call.
      \item \texttt{bi-lipschitz} is the default branch of the released code. With
            $G=J^\top J$ (the $D\times D$ pulled-back metric) it penalizes the off-diagonal
            entries of $G$ (latent directions should stay orthogonal in feature space) and
            the diagonal entries above an upper bound $L$ (squared hinge). There is no
            lower-bound term (the released code multiplies it by $0$), so nothing in it
            prevents a direction from collapsing.
      \end{itemize}
\end{itemize}
\textbf{Which variant is the paper's.} The paper describes one regularizer only,
Eq.~(12), which is \texttt{bi-lipschitz\_dec}. The released \texttt{swiss\_roll.ipynb},
however, calls \texttt{bi-lipschitz}, with hyperparameters equal to the Swiss Roll column
of the paper's Table~3 ($\lambda_{\mathrm{reg}}=1$, $\lambda_{\text{bi-Lip}}=0.3$,
$\kappa=1$, $\epsilon=0.3$); an earlier version of that notebook shows a BLAE figure that
matches visually Figure~3 of the paper. In correspondence (October 2026) the author states that
the paper's experiments use \texttt{bi-lipschitz\_dec}, that the four variants of the code
are equivalent in theory if $\mathrm{dec}\circ\mathrm{enc}$ is the identity and orthogonal
transformations are ignored, and that \texttt{bi-lipschitz\_dec} is used because it works
best empirically. The two pieces of evidence are not reconciled here; in particular it is
not known which variant produced \cite[Figure~3]{zhan2026blae}. See \cref{app:bilip}.

\textbf{What the paper's theory covers.} The paper argues \cite[Theorem~4]{zhan2026blae}
that the bi-Lipschitz relaxation \cite[Definition~4]{zhan2026blae}, regularized as in
Eq.~(12), is \emph{admissible} \cite[Definition~3]{zhan2026blae} (the set of global minima
of the regularizer does not depend on the sampling measure of the data) with a latent
dimension $n=O(k)$, linear in the intrinsic dimension $k$ of the data manifold
$(k \leq n \leq 2k)$, whereas a hard isometric-embedding guarantee needs $n=O(k^2)$.
\footnote{According to the Cartan-Janet theorem \cite{burstin1931,cartan1927,janet1926} and the 
Nash embedding theorem \cite{nash1956}, a $k$-dimensional compact 
Riemannian manifold requires a latent dimension $n$ of $O(k^2)$ to guarantee an isometric embedding
(distance preserving); this latent dimension must satisfy 
$\frac{k(k+1)}{2} \le n \le \frac{k(3k+11)}{2}$.}
By \cite[Theorem~3]{zhan2026blae} the bounds of Eq.~(12) are, for a diffeomorphism,
equivalent to the decoder being $\kappa$-bi-Lipschitz. This covers the two-sided loss
only, and three limits apply: 
\begin{enumerate*}[label=(\roman*)]
\item admissibility is a property of the global minima of
the regularizer on its own, not of what training finds, and it is not shown for the full
loss with reconstruction (and, here, KL); 
\item Theorem~4 says that \emph{some} finite
$\kappa\ge1$ admits an embedding, it gives no bound on $\kappa$, and a large $\kappa$
weakens the constraint, so $\kappa$ is a tuned hyperparameter; 
\item nothing is claimed
for \texttt{bi-lipschitz}, which has no lower bound and an off-diagonal term.
\end{enumerate*}

This is a \emph{trained regularizer}, not a proof of injectivity, and it is unproven at ImageNet 
scale: the paper's own experiments are Swiss Roll, dSprites, MNIST, CIFAR-10, Bird, and Teapot.\\

\textbf{What is reusable from the released repository, and what is not.} The repository's dataset-
specific autoencoder classes are toy-sized and toyishly-implemented (latent dims $2$--$16$, small 
fixed image sizes) and not directly usable.
What \emph{is} architecture-agnostic and reusable: the injective loss (it takes a latent batch and a
geodesic sub-table, nothing dataset-specific), the bi-Lipschitz term (it takes a decode function and a
latent batch), and the idea of the geodesic-distance table, whose computation is replaced here by a
bounded-cost version (\cref{sec:pseudoinj:gotchas}). \textbf{No VAE variant is released}: a stochastic BL-VAE is 
described only in the paper's Appendix~C.6.2, demoed on Swiss Roll, and never shipped in the code 
(a repository search for VAE/reparameterization/log-variance/KL code returns nothing in Python 
files; there's a Jupyter notebook with some VAE-denoted variables, but their examination shows that 
this is not a true VAE).

\subsection{Why a VAE head, and not a deterministic autoencoder}
\label{sec:pseudoinj:jacobian}
\textbf{The question.} The exact change-of-variables objective of \cref{eq:flow-nll} needs a volume
term. Neither IN-VAE's encoder nor a BLAE-regularized head is a square, exactly invertible map, so the
term is the Gram determinant $\det(J^\top J)^{1/2}$ of \cref{sec:flow:injective}, not an ordinary
determinant. The question is whether this objective can be used for the head. An earlier version of this
note said that $J$ ``cannot be computed''. That statement is too strong, and the justification below
replaces it.

\textbf{What is and is not the obstacle.}
\begin{itemize}[leftmargin=1.5em]
\item \emph{Computing $J$ is not the obstacle.} The trainable decoder maps a latent of dimension $D\approx10$ to
      the image-side tensor, so its Jacobian has only $D$ columns and $J^\top J$ is a $D\times D$
      matrix. Forward-mode differentiation gives $J$ with about $D$ passes per sample. This is exactly
      what the bi-Lipschitz term of \cref{sec:pseudoinj:blae} already does when it evaluates the decoder
      Jacobian. That term is a regularizer, however, and only needs a hinge penalty on the
      singular values of $J$ (or on the entries of $J^\top J$). A likelihood needs the exact
      $\log\det$ and its gradient at every step.
\item \emph{Cost is a real but secondary obstacle.} Backpropagating through $\log\det(J^\top J)$ means
      differentiating through forward-mode Jacobians of a convolutional decoder with attention, at every
      training step and for every sample. The attention blocks must also be run with the unfused (math)
      backend, because the fused kernels have no forward-mode rule. This is affordable for a
      regularizer weighted by a small coefficient and applied to a fraction of the batch, but it is a
      heavy price for the main objective.
\item \emph{The Gram determinant does not factorize over stages.} For square maps, $\log|\det|$ of a
      composition is the sum of the per-stage terms, which is what made the flow section tractable
      (\cref{eq:flow-jac-split}). For non-square maps it is not. The volume term of the composite
      ``frozen IN-VAE decoder after head decoder'' is not the sum of a backbone term and a head term, so
      the frozen backbone cannot be handled separately.
\item \emph{The main obstacle: the density is degenerate.} A deterministic decoder from a
      $D$-dimensional latent has an image that is a $D$-dimensional manifold inside a much
      larger space. The pushforward of $p_{\hat Z}$ is then supported on that manifold and has no density
      with respect to Lebesgue measure on the large space. The change-of-variables formula yields a
      density only with respect to the surface measure of the manifold, and it is meaningful only for
      points that lie on it. Real images (or their cached embeddings) never lie exactly on it, so
      $\log p_X(x)$ is undefined without an additional off-manifold noise model. This holds no matter how
      cheaply the Gram determinant could be computed.
\end{itemize}

\textbf{The rejected first candidate.} 
The first idea was to keep BLAE's deterministic autoencoder
and evaluate M1's prior at the single encoded point $\hat z=\mathrm{Enc}(x)$, as in
\cref{eq:flow-prior-term}, with no volume term. This silently replaces the target $\log p_X(x)$ by
$\log p_{\hat Z}(\hat z\mid u)$, which is a poor proxy to the extent that the encoder is non-injective.
Nothing in that loss bounds or even reports the gap.

\textbf{Decision: use a VAE for the trainable head.} A VAE needs neither the Gram determinant nor the
manifold assumption. The Gaussian decoder with fixed variance is exactly the off-manifold noise model
that makes the density on the large space well defined, and the ELBO then requires no Jacobian at all.
This is why Ng et al.'s estimator (\cref{app:code}) and \nameref{sec:archA}/\nameref{sec:archB} all use
an ELBO. The price is the usual, already accepted approximation: $q(\hat Z\mid X)$ only approximates the
true posterior, and the reconstruction term only penalizes the cases where decoding fails to invert
encoding. The Jacobian then appears in exactly one place, the BLAE bi-Lipschitz regularizer, where an
approximate, weighted use is sufficient.

\subsection{The resulting architecture}
\label{sec:pseudoinj:arch}
\begin{enumerate}[label=(\arabic*),leftmargin=2em]
\item \textbf{Frozen backbone.} IN-VAE's pretrained encoder (\cref{sec:pseudoinj:invae}), run once 
       per image, cached, exactly as \nameref{sec:archB} caches $\tilde x=\mathrm{BB}(x)$ -- except 
       here $\tilde x$ is the spatial IN-VAE latent mean, a $32\times16\times16$ tensor, not a pooled 
       ResNet vector.
%-----------------
\item \textbf{Trainable head} (\texttt{head.py}). A \emph{fresh, untrained} instance of Hugging 
      Face's \linebreak
      \texttt{diffusers.AutoencoderKL} \cite{aekl} (not a pretrained checkpoint), 
      used \emph{unmodified} -- rather 
      than editing its \texttt{quant\_conv} and \texttt{post\_quant\_conv} internals, two small 
      trainable linear layers sit outside it and convert between its native spatial latent 
      and M1's flat vector.

      \textbf{Sizing the stock module.} \texttt{AutoencoderKL} \cite{aekl} is configured, but not 
      altered internally, to fit the $32\times16\times16$ IN-VAE input:
      \begin{itemize}[leftmargin=1.3em]
      \item In diffusers the last encoder stage does not downsample, so \texttt{N} stages give 
            \texttt{N-1} halvings. Three stages are used,
            \texttt{down\_block\_types = ("DownEncoderBlock2D",} \texttt{"DownEncoderBlock2D",}
            \texttt{"DownEncoderBlock2D")}
            ($16\to8\to4$), with the symmetric \texttt{up\_block\_types} triple;
      \item \texttt{block\_out\_channels = (32, 64, 128)}, each divisible by the GroupNorm group
            count ($32$);
      \item \texttt{layers\_per\_block = 1};
      \item \texttt{in\_channels = out\_channels = 32};
      \item \texttt{latent\_channels = 4} (the stock default, a hyperparameter); this is \emph{not}
            M1's $\sim\!10$-dim latent -- that reduction happens entirely in the linear layers below,
            outside the module.
      \end{itemize}
      With this config the module's own bottleneck is $4\times4\times4=64$ scalars. The code does not
      assume this: it measures the bottleneck shape by a dry run at construction and exposes it, so
      the number should always be read from the built module and not computed by hand.

      \textbf{Which vector leaves the module.} The module encodes to its own Gaussian
      (mean and log-variance). M1 needs exactly one posterior, $q(\hat Z\mid x)$ over the $D$ M1
      latents, so by default only the module's \emph{mean} is used and its internal variance is
      ignored; all noise comes from the reparameterization of the M1 posterior. (Sampling the internal
      Gaussian too would inject a second, unmodelled noise source between $x$ and $\hat z$; it is
      available as an option, \texttt{internal\_latent="sample"}, and is not recommended.) The
      module's internal KL loss is never computed.

      \textbf{Pre-linear layer (after \texttt{AutoencoderKL.encode}, before M1).} The module's
      $4\times4\times4$ mean is flattened ($64$ scalars) and a single linear layer maps it to
      $2D$ scalars, the first $D$ being $\hat\mu$ and the last $D$ being $\hat{\log\sigma^2}$ (clamped to
      $[-10,10]$ for numerical safety), where $D=n_c+n_s$. This linear layer is the actual
      dimensionality-reducing step; \texttt{AutoencoderKL} itself is never told about, and never
      computes, the $D$-dim target.

      \textbf{Post-linear layer (after M1's prior/loss, before \texttt{AutoencoderKL.decode}).} A single
      linear layer expands the sampled $D$-dim $\hat z$ back to a flat $64$-vector, reshaped to
      $4\times4\times4$ and passed into stock \texttt{AutoencoderKL.decode} unmodified.

      \textbf{Why this is preferred over editing the module.} The pre/post linear layers are the only
      hand-written, unvalidated pieces; \texttt{AutoencoderKL}'s own encode/decode path and internal
      conv blocks stay exactly as tested and released, with no risk of 
      a silent behavioral change from touching \texttt{quant\_conv}/\texttt{post\_quant\_conv} directly. 
      The cost is one extra pair of thin layers and one more bottleneck seam (module output $\to$ M1
      vector) to account for when tracing where distortion enters the pipeline 
      (\cref{sec:pseudoinj:gotchas}). Because the module's internal variance branch is computed but
      unused in the default mode, its parameters receive no gradient.
%-----------------
\item \textbf{M1 prior, unchanged in structure.} The content/style ANM prior of \cref{sec:use} -- the
      content mechanism, the noise-scale networks, the adjacency \texttt{adj\_mat}, sink-freezing --
      sits on top of the head's output as in \cref{app:code}, with the domain conditioning split by block
      as planned there (\texttt{m1net.py}); only the recognition
      network $q(\hat Z\mid X)$ feeding it is the new head.
\item \textbf{BLAE losses, added to the head's training, computed on $\hat\mu$.} The injective loss
      is evaluated on the posterior mean $\hat\mu$ and the bi-Lipschitz term on the decoder Jacobian
      evaluated at $\hat\mu$ (never at a noisy sample $\hat z=\hat\mu+\epsilon$, since both are
      statements about a deterministic map -- the reparameterization noise must not enter these
      terms). The geodesic-distance table (\texttt{GeoD}), needed only by the injective loss, is
      built once from the cached IN-VAE embeddings of the training-location images.
      
      It might appear at the first glance that BLAE is redundant since the model already includes
      the reconstruction loss (which is also done in IN-VAE).
      The short picture is that reconstruction loss pushes toward injectivity, but only weakly. How 
      weakly depends on the bottleneck, and the head's bottleneck is very tight.
      \begin{itemize}
      \item \textbf{Why IN-VAE gets away without BLAE.} Its latent is 8192 numbers for a 256
         $\times$256 image, so reconstruction can be nearly lossless. Almost nothing has to be 
         merged, and reconstruction alone keeps it close to invertible.
      \item \textbf{Why the head is different.} The head compresses 8192 numbers (really 64 inside 
        the AutoencoderKL) down to about 10. At that size, perfect reconstruction is impossible. 
        Three things then work against injectivity:
        \begin{enumerate}
	    \item \textbf{Merging cheap directions.} Reconstruction (MSE) only penalizes what is 
	       expensive to lose. Subtle directions, such as faint camera or location cues, cost little 
	       in MSE, so the head can collapse them, and those are exactly the directions the style 
	       block needs.
        \item \textbf{The KL term.} It pulls the posterior toward the prior, which actively rewards 
           merging inputs. Reconstruction pushes against it, but nothing sets a floor on how much 
           stays separated.
		\item \textbf{No control on the inverse.} Reconstruction says nothing about how 
		   well-conditioned the decoder is, and the theory needs a smooth inverse, not just a 
		   one-to-one map.
		\end{enumerate}
		\item \textbf{What BLAE adds.} INJ sets an explicit floor, so latent distances can't fall 
		   below 0.3 of the input geodesic distances. BILIP controls the decoder's metric: the
		   variant \texttt{bi-lipschitz\_dec} keeps the singular values of the decoder Jacobian
		   in $[1/\kappa,\kappa]$, hence well-conditioned; the variant \texttt{bi-lipschitz}
		   bounds only the stretch and the overlap of the latent directions, with no lower
		   bound.
		\item \textbf{Honest caveat.} BLAE is a hedge, not a proven need. It is untested at this 
		   scale and untested together with a KL term, as the note already says. If the first runs 
		   show distinct inputs staying apart without it, you could set \texttt{lambda\_inj} and 
		   \texttt{lambda\_bilip} to 0 and drop it. Cheap check: compare the latent-to-geodesic 
		   distance ratio on held-out pairs with and without INJ.
		\end{itemize}
\end{enumerate}
The resulting per-image loss, replacing \texttt{Trainer.step} of \cref{app:code} on the head side:
\begin{equation}
\begin{aligned}
\mathcal L(x,u) &= \lambda_{\mathrm{kl}}\,\mathrm{KL}\bigl(q(\hat Z\mid x)\,\|\,p_{\hat Z}(\hat Z\mid u)\bigr) \\
&+ \lambda_{\mathrm{rec}}\,\mathrm{recon}(\tilde x,\hat{\tilde x}) \\
&+ \lambda_{\mathrm{inj}}\,\ell_{\mathrm{inj}}(\hat\mu,\mathtt{GeoD}) \\
&+ \lambda_{\mathrm{biLip}}\,\ell_{\mathrm{biLip}}(\hat\mu;\,\mathrm{decode}) \\
&+ \lambda_{\mathrm{sparse}}\,\ell_{\mathrm{sparse}}(\hat A) \\
&+ \lambda_{\mathrm{moral}}\,\ell_{\mathrm{moral}}(\hat A, A^{t-1}),\footnotemark\\
&\quad A^{t-1}\ \text{is the binary adjacency matrix estimated in the previous} \\
&\quad \text{(i.e.,}\ (t\!-\!1)\text{-th) iteration}.
\end{aligned}
\label{eq:pseudoinj-loss}
\end{equation}
\footnotetext{Ng implementation dropped the moral loss term in their implementation --
see \cref{app:code:lossterms}. Here it is implemented in \texttt{losses.py}, with target weight $0$ for
the first runs.}%
where $\tilde x$ is the cached IN-VAE embedding (the reconstruction target, one level removed from the raw
image, as in \nameref{sec:archB}), and the first, second and fifth terms are exactly \cref{app:code}'s
\texttt{loss\_kl}, \texttt{loss\_rec} and \texttt{loss\_sparsity}; the KL term is evaluated, as there,
as the single-sample estimate $\log q(\hat z\mid x)-\log p(\hat z\mid u)$ summed over the $D$ latents,
because the content prior mean depends on $\hat z$ itself and no analytic KL exists.
\emph{No Jacobian term appears anywhere
in \cref{eq:pseudoinj-loss} except inside $\ell_{\mathrm{biLip}}$}, by the decision of
\cref{sec:pseudoinj:jacobian}. The weights are not constants: when each term starts, ramps and
switches off is the subject of \cref{sec:schedule}; the starting targets are $\lambda_{\mathrm{inj}}=0.1$
and $\lambda_{\mathrm{biLip}}=10^{-4}$, both guesses for this setting. BLAE's own values
(its Table~3: $1$ to $30$ for the injective term, $0.1$ to $0.3$ for the bi-Lipschitz
term) are on other loss scales and do not transfer, but they suggest that ours may be too
small; the gradient-scale probe of \cref{sec:schedule:gradlog} is the tool to check.

\subsection{Why this is more principled than plain Option B -- and what it still is not}
\label{sec:pseudoinj:principled}
Both stages of this pipeline carry an explicit, measurable regularizer toward injectivity: IN-VAE's
reconstruction training (rewards approximate invertibility directly, unlike a classification objective);
the head's injective and bi-Lipschitz losses (the first bounds the ratio of latent to geodesic
distances to $[0.3,1]$; the second, in the variant \texttt{bi-lipschitz\_dec}, keeps the
singular values of the decoder Jacobian in $[1/\kappa,\kappa]$, and in the variant
\texttt{bi-lipschitz} bounds only the diagonal of the pulled-back metric by $L$ and
penalizes its off-diagonal; each with a stated target).
Plain \nameref{sec:archB} has neither -- \cref{sec:archB:gap}'s gap is totally unexamined there.
This is genuinely better: instead of an unknown, unbounded gap, the deviation here has stated targets
(ratio in $[0.3,1]$; singular values in $[1/\kappa,\kappa]$ for \texttt{bi-lipschitz\_dec},
diagonal of the pulled-back metric at most $L$ for \texttt{bi-lipschitz}) against which the
trained model can be measured after the fact, for example by the fraction of held-out pairs
whose ratio falls outside the band, or (for \texttt{bi-lipschitz\_dec}) the fraction of
held-out latent points at which a singular value of the decoder Jacobian falls outside
$[1/\kappa,\kappa]$. The regularizers themselves do not report that gap during training.

It is not a proof of injectivity, and \cref{thm:ng}'s hypothesis -- $g$ an exact $\mathrm{C}^2$ 
diffeomorphism onto
its image -- is still, strictly, violated by both IN-VAE and the head, in exactly the same
\emph{category} of gap \cref{sec:archB:gap} already names for plain Option B. BLAE's
admissibility statement (\cref{sec:pseudoinj:blae}) concerns the global minima of the
two-sided regularizer alone and does not carry over to the trained combination used here.
The honest claim is:
\textbf{bounded and diagnosable distortion, not solved injectivity.} This should be stated exactly this
plainly wherever this pipeline is invoked elsewhere in the note, the same way \cref{sec:archB:gap} states
its own gap without softening it.

\subsection{Gotchas}
\label{sec:pseudoinj:gotchas}
\begin{itemize}[leftmargin=1.5em]
\item \textbf{KL vs.\ injective/bi-Lipschitz tension, and the limits of what can be said about it.} The
      KL term in \cref{eq:pseudoinj-loss} rewards posterior compression toward the prior; the injective and
      bi-Lipschitz terms reward keeping distinct inputs' encodings apart. These pull in opposite
      directions. The most that can honestly be said at present: Zhan et al.\ state that BLAE's losses can
      be added to a VAE, and presumably tested this on a toy example, but \textbf{no such implementation
      was released} (\cref{sec:pseudoinj:blae}), so this note's combination of a fresh
      \texttt{AutoencoderKL} head with BLAE's losses is unverified engineering, not a reproduction of a
      published result. $\lambda_{\mathrm{kl}}$ against $\lambda_{\mathrm{inj}},\lambda_{\mathrm{biLip}}$
      needs to be tuned empirically, with no prior result to anchor the starting point; the gradient-scale
      probe of \cref{sec:schedule:gradlog} is the tool for that.
\item \textbf{Which BILIP variant.} The paper's loss (Eq.~(12), \texttt{bi-lipschitz\_dec})
      and the loss the released Swiss Roll notebook calls (\texttt{bi-lipschitz}) differ,
      and the author states that the paper used the former (\cref{sec:pseudoinj:blae}).
      Both are implemented and the choice is the user's
      (\texttt{loss.bilip\_variant}); the configuration default is \texttt{bi-lipschitz}.
      The bound \texttt{loss.bilip\_L} is $L$ in one and $\kappa\ge1$ in the other, and the
      two numbers are not on the same scale: with $G$ diagonal, $\mathrm{diag}(G)\le L$
      means $\sigma_{\max}\le\sqrt{L}$. Switching variant means re-tuning the weight.
\item \textbf{Extreme compression ratio.} \texttt{AutoencoderKL}'s stock configurations target hundreds 
      to thousands of latent channels, not $\sim\!10$; squeezing this far raises real underfitting/
      posterior-collapse risk. \Cref{sec:pseudoinj:arch} above hand-tunes depth and channel width down 
      for this reason, but the $4\times4\times4=64$ scalars $\to2D=20$ scalars bottleneck introduced there 
      is itself a 
      further, unusually aggressive compression step (flattening plus one linear layer) with no 
      precedent in the stock class to calibrate against.
\item \textbf{Fresh initialization, no pretraining head start.} Unlike IN-VAE, the head is trained from
      scratch on $\sim\!18\mathrm{k}$ TI images alone.
\item \textbf{BLAE losses must be computed on $\hat\mu$, never on the sampled $\hat z$} -- this needs to 
      be explicit in the loss code, not left implicit, since it is easy to accidentally apply it after 
      the reparameterization step. In \texttt{losses.py} both terms read \texttt{out["mu"]}.
\item \textbf{No VAE implementation exists in the BLAE repository at all}; combining a tested
      \texttt{AutoencoderKL} \cite{aekl} with a from-scratch reimplementation of BLAE's loss terms is 
      novel engineering that must be built and validated, not assumed to inherit the paper's toy-scale 
      results.
\item \textbf{Spatial, not pooled, embeddings, and a non-standard bottleneck.} IN-VAE's output is a
      $32\times16\times16$ tensor, unlike \nameref{sec:archB}'s flat pooled $\sim\!3072$-dim vector; the
      head must be conv-based to consume this properly, not a bare MLP as in \cref{app:code}'s
      \texttt{encoder\_mu}/\texttt{encoder\_logvar}. Because stock \texttt{AutoencoderKL} \cite{aekl} 
      has no built-in path from a spatial bottleneck to a flat per-image vector, the two linear layers
      of \cref{sec:pseudoinj:arch} (outside the module, which stays unmodified) are hand-written and
      untested code, not a configuration of an existing, validated path.
\item \textbf{Forward-mode differentiation in BILIP.} The fused attention kernels in
      \texttt{AutoencoderKL} have no forward-mode rule, so the plain (math) attention backend is forced
      inside the bi-Lipschitz term. It costs about $D$ decoder passes per sample on a random fraction of
      the batch, which is why it is the most expensive term and is started last (\cref{sec:schedule}).
      The variant \texttt{bi-lipschitz\_dec} adds one \texttt{torch.linalg.svdvals} of the
      $P\times D$ Jacobian per row ($P=8192$ output scalars, $D\approx10$); the released
      code calls \texttt{torch.linalg.matrix\_norm} twice (orders $2$ and $-2$), which
      PyTorch implements as two full \texttt{svdvals} calls, so one call suffices.
\item \textbf{Resolution.} IN-VAE candidates (including the chosen one) are pretrained at 
      $256$px, and the feature-extraction and dataset code of this pipeline (\texttt{extract\_features.py},
      \texttt{ti\_dataset.py}) use $256\times256$ images and the matching bounding-box transform. The
      sections on \nameref{sec:archB}, which assume $224$px, are not updated by this and refer to the
      ResNet-50 pipeline only.
\item \textbf{Screened candidates.} E2E-VAE and MAETok/STELLAR carry alignment or semantic-shaping losses
      that risk discarding style/location signal, the same failure mode \cref{sec:pretrain} already flags
      for supervised ImageNet pretraining; neither is used here, and any candidate -- including the chosen
      IN-VAE -- still needs to clear \cref{app:probe}'s linear-probe screen before being trusted.
\item \textbf{The geodesic-distance table (\texttt{GeoD}) cost, now one stage removed from pixels.} Building
      \texttt{GeoD} on the cached IN-VAE embeddings ($N\!\approx\!18\mathrm{k}$, still $\sim\!8192$-dim)
      is a one-time precompute, run once per choice of backbone/embedding (not per epoch, not per
      minibatch). It is implemented in \texttt{geodesic.py} as follows.
      \begin{itemize}[leftmargin=1.3em]
      \item \emph{Optional PCA}, $8192\to256$ (seeded), before the neighbour search, so all distances
            are Euclidean distances in the PCA subspace (Johnson-Lindenstrauss-style, $\sim\!32\times$
            cheaper).
      \item \emph{Pairwise-distance step}, $O(N^2d')$ time. Naive broadcasting would try to materialize an
            $N\times N\times d$ tensor ($\sim\!10$TB at $N=18\mathrm{k}$, $d=8192$) -- infeasible. The
            code uses the Gram identity $\|x-y\|^2=\|x\|^2+\|y\|^2-2x^\top y$ in row chunks (one 
            $\mathrm{matmul}$ per chunk, peak memory \linebreak
            $O(N \cdot \mathrm{chunk})$, on GPU if available), keeps the $k$ nearest
            neighbours of each point, and symmetrizes the graph. Float32 cancellation gives edge lengths
            accurate to about $10^{-3}$, irrelevant for a regularizer. If the $k$-NN graph is
            disconnected, $k$ is doubled up to a maximum and the step repeated; if it is still
            disconnected an error is raised, since geodesic distances are infinite between components.
      \item \emph{All-pairs shortest-path step}, $O(S(E+N\log N))$ for $S$ sources and $E\approx Nk$
            edges: Dijkstra from each source over the sparse graph, sharded across worker processes
            (embarrassingly parallel). The weights are non-negative, so plain Dijkstra is the right
            choice; Johnson's algorithm exists for negative weights and has no advantage here.
      \item \emph{Storage modes.} \texttt{"full"}: the exact $N\times N$ table ($\sim\!1.3$GB in float32,
            $\sim\!650$MB in float16, which is acceptable because geodesic distances are a regularization
            target, optionally a disk memmap). \texttt{"landmark"}: only an $L\times N$ table from $L$
            random landmarks ($L=2000$: $\sim\!144$MB), with the sub-table approximated as
            $D_{ij}\approx\min_l\bigl(d(l,i)+d(l,j)\bigr)$. This is an \emph{upper bound}: exact when $i$
            or $j$ is a landmark or lies on a shortest path through one, and otherwise an overestimate
            (triangle inequality). An overestimated $D$ lowers the latent/geodesic ratio in the injective
            loss and so biases it toward pushing pairs apart; prefer \texttt{"full"} when $N^2$ fits
            in RAM.
      \end{itemize}
\item \textbf{Memory.} The table lives on CPU and is never copied to the GPU in full: per minibatch the
      $B\times B$ sub-table for the batch's dataset row ids is sliced on CPU and only that slice moves to
      the GPU. The real risk was upstream, in the pairwise-distance step (doing it naively on GPU can
      exhaust GPU memory before \texttt{GeoD} exists), which the chunked Gram computation avoids. The
      table is indexed by the row ids of the dataset it was built from, so those ids must stay fixed
      between building the table and training. It is built on all rows of the selected training
      locations (training and validation rows together).
\item \textbf{Still not exact injectivity.} As stated in \cref{sec:pseudoinj:principled}, this pipeline
      bounds and quantifies the gap from \cref{thm:ng}'s exact-diffeomorphism hypothesis; it does not
      close it. Any downstream use of this note's identifiability results should carry this caveat forward
      explicitly.
\end{itemize}
